# 手机版本冲突恢复修复（2026-10-29）

## 现象与证据边界

服务器日志中有 GET /v1/reports 200、GET /v1/sync/changes 200、POST /v1/sync/batches 200/409，以及少量 401。Caddy 后的来源地址相同，不能据此把每一条请求归到手机或电脑。持续 409 说明旧基线上传被拒绝，401 需要核对当次使用的凭据；不能通过不停重试、关掉版本检查或删除数据库解决。

旧恢复按钮在一次点击中发起下载、立即弹第二次确认，然后才读云端并重载。失败提示与同步状态分散，iPhone 用户无法区分取消、下载、等待、恢复失败或已完成。缺少待上传项时，旧同步按钮不请求服务器也会显示“已同步版本0”。

## 本次修复

- 独立的“导出恢复前备份”按钮，等待用户确认文件确实保存后再勾选确认框。下载不自动弹出恢复确认；Blob 下载地址保留更久。
- 恢复只有一个独立确认，明确展示读取中、完成或失败；成功后重新加载本机数据模型并刷新界面，不依赖 Safari 导航或重载。
- 恢复时等待在途同步，暂停自动上传；读取期间或备份后记录被本页/其他页修改，则拒绝用旧备份授权覆盖新记录。
- 401/409 显式显示状态码并暂停自动重试，保留本地队列。没有待上传项也须核对云端版本和凭据，不把版本号单独改成服务器数值。
- 读取云端基线保持固定分页目标；原 V1 本地键、日志时间和云端历史报告不变。不修改后台数据库、模型/飞书/定时器配置。
- Service Worker 缓存版本更新；不会清 localStorage 或要求卸载、清 Safari 数据。

## 用户恢复步骤

仅在新预览页操作，先关闭电脑测试页及其他新预览页；原 GitHub Pages 计时页保留。

1. 确认页面出现“导出恢复前备份”和保存确认框。
2. 单独导出备份，在 iPhone“文件”中确认保存。
3. 回到页面勾选已保存，再点“冲突恢复：采用云端副本”。这会替换新测试页本地记录和待上传修改；有必须保留的手机独有记录时先停下，保留备份后决定合并方式。
4. 确认后等待“恢复完成”，页面会立即显示最新云端版本和记录，无需自动刷新。然后只用手机录入一条测试记录，确认同步版本上升。
5. 电脑如需使用，仅查看已有报告，不同时修改记录。当前仍是单设备使用方案，不实现多设备自动合并。

## 验证

前端 30 项 Node 用例通过，包含新增 7 项：空队列鉴权、旧基线拒绝、读取期间新修改继续同步、明确恢复队列与基线、并发修改保护、分页不一致保护、凭据空白及错误码。

本地 Chromium 390×844 视口、同预览站 CSP、合成 API 响应通过：409 后停止重复上传；未保存备份不恢复；下载没有紧接第二次弹窗；一次确认后读云端并不重载更新界面；下一次到达计时成功上传；空队列 401 不再显示成功。没有调用真实业务服务，不能代替更新后的 iPhone 实机验收。

开发机复现：

```bash
env -u NODE_OPTIONS node --test --test-isolation=none tests/*.test.js
# 开发机另起仅回环静态服务：python3 -m http.server 18001 --bind 127.0.0.1
node tests/recovery-browser.cjs
```

## 预览站更新方式

仅更新 /srv/timemap-preview/current 指向的新静态版本，不部署 main，不重建或重启后端，不改数据库/Caddy。原后端固定 e1967b7，其构建记录中的前端来源为 99a893d；这份后端来源记录保持不变，静态补丁用独立 Git 提交和静态文件清单记录。

不要在正在用于构建验证的 /opt/timemap-test/current/frontend 执行 git pull/checkout 改变 HEAD，这会破坏后端工具的固定提交检查。正确方式是仅 fetch 对象，再为补丁 SHA 添加独立 detached worktree，检查并复制静态文件到新版本目录，最后原子切换预览链接。失败时切回之前的链接，保留手机本地和服务器数据。
